# PREREG addendum: the 32k live suite

Written 2026-10-31, before any result of this suite. `PREREG.md` is unchanged and still governs the main run. The first half of this file fixes the setup, the second half what is measured and how it is read.

**Why.** At the main run's 128k window, 52 of 53 live cuts kept the whole current task word for word (R&D, `rnd/postcut.py`), so the main live run never tests a summary on work in progress. A 32k window makes tasks larger than the room common, so cuts must summarise part of the task at hand. Decision by the CEO.

## Setup

- **Same** harness (`harness/live.py`), prompts, container tools, grader, caps (30 minutes of working time, 120 turns) and rules as the main run. A chain with a task that ended in a provider error is redone, as in the main run.
- **Model**, for both arms: DeepSeek V4.1 Flash, the dated snapshot `deepseek/deepseek-v4.1-flash-1017` through OpenRouter (not the moving `-latest` alias), pinned to **one upstream, DigitalOcean, with no fallback** (Pi's `openRouterRouting`: `only`, `allow_fallbacks: false`), thinking `high`, through `OPENROUTER_API_KEY` (per-token, approved by the user as the fallback; spend reported). The window is forced to 32,768 and the reply cap to 16,384 in each arm's isolated agent dir (`modelOverrides`), so Pi's reserve is 16,384 and the input room 16,384 for both arms. The model's own window is 1M; without the override neither compactor would see 32k. Pinning is not cosmetic: upstreams count tokens differently (for the same request with pi-tuck's tool schemas Wafer reported 5,715 prompt tokens where Relace, OpenInference, DigitalOcean and Morph reported 2,155 to 2,167), and pi-tuck calibrates on reported usage. The first start of this suite used the alias and ran arm A on one upstream and arm B on three; it was stopped, set aside and never read (`DEVIATIONS.md`). `analysis/upstreams.py` samples a run's requests and reports the upstream that served them; the results include that check.
- **Reserve 16,384** (the reserve the user approved with R&D's repairs; it was changed to 8,192 for a while on a finding that was wrong, see below). The room is 16,384 and about 23% of tasks exceed it, which is the point of the suite. **Retracted finding:** an early smoke at this reserve made pi-tuck refuse ("mandatory context cannot fit") and the aborted run left the next task aborted. That was caused by the alias routing that request to Wafer, which over-counted pi-tuck's tool schemas (above), not by pi-tuck's design. On the pinned upstream the same 3-task chain at this reserve ran with no refusal for Pi's compaction, pi-tuck 1.0.1 and pi-tuck 1.0.3 (1.0.3 cut 19 times in the three tasks, each cut freeing a median of 51% of the room and none under a tenth). The earlier smokes are kept under `runs/smoke32-old/` and `runs/smoke32r16/` and are not results.
- **`keepRecentTokens` = 3,333** for Pi's native compaction: the main run's 20,000 of a 98,304 room scaled to 16,384. Same setting in both arms. Pi-tuck has no such setting.
- **Arms.** A: Pi's built-in compaction. B: pi-tuck **v1.0.3, commit `656f77a`** (npm latest at the time, lean cuts and the small-window tail fix included), semantic recall on. This is not the main run's pin (1.0.1, `d71234a`), by decision of the CEO: 1.0.1 re-cuts every round or two at small windows (a defect fixed after it), so testing it here would measure a known bug, not what users get. The main run is unaffected and stays at 1.0.1. An earlier plan for a third arm (1.0.1 plus only the tail fix) was dropped for the same reason.
- **Arm M (secondary, added before any pinned result).** Pi's built-in compaction, as in A, plus **observation masking** as in "The Complexity Trap" (Lindenbauer et al., 2025): on each request, tool outputs older than the last 10 turns (assistant messages) are replaced by a placeholder, while the agent's reasoning and its tool calls stay (`harness/mask-extension.ts`, window M = 10 as in the paper's main setting). Pi's compaction stays on as the fallback, because masked histories still grow with prompts and reasoning over a 30-task chain. M is the cheap published baseline that paper found as good as LLM summaries; it is run on the same chains, in step with A and B, and read as A against M and B against M in the same form as B against A. Source: BACKLOG item 4(b). The paper's turn-count LLM summary (N = 21, M = 10) is not run here; it stays on the backlog.
- **Tasks.** Chains of 30 tasks, same order in both arms, seed 20261031 (`harness/select_w32.py`). **First batch, run now: five chains** (`t01`-`t05`, 150 per arm), drawn from the eligible instances that no running main chain uses: the 61 the main draw left over, the 16 of the pilot and the 90 of the finished main chains `s01`-`s03` (167 in all, 150 used). Disjoint from `s04`-`s10`, so the suites never share a task image at the same time. **Second batch, after the main run has finished and freed its disk and images: five more chains** (`t06`-`t10`), drawn with the same seed from the 17 tasks the first batch left plus the tasks of `s04`-`s10`. The CEO set five plus five because three chains give about 25 affected tasks and about two discordant pairs, too few to decide anything (R&D's count from its 32k replays).
- **Spend.** Tokens and dollars come from Pi's usage cost per session (not the account total, which other work shares). Tripwire (eval lead's pick): if the suite's cumulative cost passes $60, stop and ask the CEO.

## What counts as summarising the current task

For each compaction entry in a session file, the task is the one whose prompt entry most recently precedes it. The cut **summarises part of the current task** if the entry named by `firstKeptEntryId` comes after that task's prompt entry (R&D's rule in `rnd/postcut.py`). Per arm.

The **primary subset S** is the paired tasks where such a cut happened in A or in B (either). Sensitivity subsets: in A only, in B only, in both. S is defined from the runs themselves, so it is not blind to the arm; this is why all paired tasks are reported next to it.

## Readouts

1. **Resolve rate**, B against A, paired by chain and task: the difference in points (B minus A), discordant counts, and a one-sided 95% lower bound from a paired bootstrap over tasks (10,000 draws, seed 1). Reported on S and on all paired tasks, and per chain. Tasks in one chain share a context, so the task-level interval is narrower than the truth; a bootstrap over chains is shown beside it once at least ten chains are in, and the per-chain differences always.
2. **Turns per task**, B against A: mean paired difference with the same bootstrap, on S and on all paired tasks, and on tasks both resolved.
3. **Arm M:** the readouts above for M against A and for B against M, on S and on all paired tasks (S is defined for M as for B, with M's own cuts); tokens per session for all three arms.
4. **Secondary:** tokens per session (input plus output with and without cache reads); cuts per session and the context carried after a cut, from the session files (`analysis/sessionlog.py`); the share of tasks stopped by the wall or turn cap or ended in a provider error, per arm; pi-tuck refusals ("mandatory context cannot fit") per arm; spend.
5. **Claim form**, as for Test 2: report the bound. A statement of "no loss larger than X points" is made only for an X the lower bound supports. No pass threshold is set before the result.

## Rules

- **Batches.** The first look is the first batch alone, and its result is reported as such. The second batch is part of the plan, not a response to the first batch's sign; the final tables report the two batches separately and pooled. No further chains are added except by the CEO's decision on interval width.
- **Setup misbehaves.** If in both arms more than 40% of tasks end stopped by a cap or in a provider error, the window is the problem, not a compactor: stop and ask the CEO. A pi-tuck-only failure (refusals, aborted runs) is a result and is reported, not a reason to stop.
- **Not claimed.** Nothing here carries to other models or windows, and the suite does not replace the main run's claims. A pi-tuck refusal that ends a run counts as unresolved, like any task not resolved.

## Addendum, 2026-10-31 13:23 CDT: refusals and the nominal window (written after t01 and t02 were read)

Chains t01 and t02 (arms A, B, M) were read to explain the errors in t01-B. What they show, and what is added to the readouts. The primary readouts above are unchanged and still count a refusal as unresolved.

- **The errors in B are pi-tuck refusals, not provider errors.** On the pinned DigitalOcean route, pi-tuck 1.0.3 answered "mandatory context cannot fit or reduce the request budget" and ended the run: t01-B tasks 27-30 (4 of 30), t02-B tasks 10-30 (21 of 30, 7 resolved). Every provider-reported prompt before the first refusal was far below the room (6,274 tokens at t01 task 27, 13,674 at t02 task 10); each first refusal follows a single tool result of 33,597 characters (t01) or 50,880 characters (t02) that the next request had to carry. After the first refusal the session did not recover: every later prompt in the chain was refused at once (0.04-0.1 s, no request sent). So 23 of the 25 refused tasks are the aftermath of two refusals, not independent events. The earlier retraction (the smoke refusal came from Wafer's token over-count) stands for that smoke; this is a second, different cause. The code path is `session_before_compact` / the draft's floor check in `src/tuck.ts` (`fits(base)`); why the later prompts cannot cut the oversize result away is a question for the pi-tuck maintainers.
- **Setup asymmetry, stated beside every 32k number.** The 32,768 window is nominal: the upstream model accepts far more. Pi's own compaction (arms A and M) acts after a run, so within a run their requests grow past the 16,384 room: A had a request over the room in 34 of 59 tasks (largest prompt 31,590 tokens), M in 30 of 56 (32,309); B in none (largest 15,073), because pi-tuck guards every request. A provider that enforces prompt plus reply cap within the window would reject those A and M requests. So A and M run with more context than the window says, and pi-tuck is the only arm held to it. This favours A and M.
- **Added secondary views** (`analysis/w32_stats.py`): per arm, tasks refused by pi-tuck, tasks with a request over the room, and the largest prompt; per comparison, the paired readout on tasks before the chain's first pi-tuck refusal and on tasks from it on. These describe the failure; they do not replace the primary readout and do not drop the refused tasks from it.
- **Not changed:** chains continue as planned (t03-t05), a refusal is not redone as a provider error (the main run's redo rule is for provider errors only), and the second batch stays as written. The word "provider error" in the driver's per-chain line and in older readout labels includes pi-tuck refusals; the counts above separate them.

## Addendum, 2026-10-31 13:25 CDT: acceptance test for a recovery fix (arm B′), fixed before any B′ result

This is the acceptance test for a fix, by the pi-tuck maintainers, of the unrecovered refusal (above). Nothing of B′ exists yet.

- **What runs.** pi-tuck at the commit the maintainers name (pinned in `PINS.md` with its hash before the first task), as arm **C** of the 32k suite (the label `C` is used because `B` is taken here; "B′" is the name in prose), on t01-t05 (150 tasks), with the same model, upstream pin, window, reserve, `keepRecentTokens`, tasks, order, prompts, grader and caps as the first batch. Arms A and M are **shared** with the first batch, not rerun beside B′: the cost is that B′ ran at a different time, stated beside every B′ number. The run starts only after the maintainers hand over a build. Command: `harness/run_live_all.py --suite w32 --tuck <fixed build> --pairs 1 --arms C --sessions t01,t02,t03,t04,t05`.
- **Dead task.** A task refused by pi-tuck before any request is sent (the notice fires on `input`, `analysis/w32_stats.py` counts these as aftermath: refused tasks that follow a refused task in the same chain, plus any refused task that has no request).
- **Pass bar (both parts must hold, on the 150 paired tasks):**
  1. **Zero dead tasks.** No task in any of the five chains is refused before a request is sent. A refusal in the middle of a run, because one request genuinely cannot fit, does not fail this part if the next prompt runs normally.
  2. **Resolved tasks no worse than B before its first refusal.** Let *d_B* be the mean paired difference (B minus A, in points) of arm B on the tasks before each chain's first refusal in the first batch (a chain with no refusal contributes all 30), pooled over t01-t05, and *d_B′* the mean paired difference (B′ minus A) on all 150 tasks. B′ passes this part if *d_B′ ≥ d_B − 3* points (the margin of `PREREG.md`). The paired difference against A cancels task difficulty.
- **Also reported, no pass line:** the one-sided 95% lower bound of B′ minus A and of B′ minus M on all tasks and on S, turns per task, requests over the room (expected none), cuts, tokens, spend, and how many tasks the fix recovers compared with B.
- **If it fails**, the results say which part and show the chains; a second fix is a new build with a new acceptance run under the same bar. The bar is not changed after seeing B′ results. A fix that makes pi-tuck truncate or drop the oversize result without a record is outside "recovery"; the maintainers' description of what the fix does is quoted in the results.
- **Not claimed:** nothing about builds other than the named commit, and the 32k result for the shipped 1.0.3 build stays as it is in the first batch.

## Definition, 2026-10-31 14:55 CDT (project decision, before any arm C result; the bar is not changed)

- **A dead task is one lost because an earlier task or prompt failed: the session carries a failure forward.** A task refused only because its own fresh tool round cannot fit the room is not dead: it counts as unresolved in the B′ minus A comparison like any other unresolved task, and it is reported separately as a count (mid-run refusals). Fixing those belongs to the clip build and its own gate, not to arm C. Arm C runs `4ea726f`; it does not wait for the clip.
- **How it is read** (`analysis/w32_stats.py`): a refused task whose refusal came before any request carried tokens (the refusal on `input`, 0-1 ms, no request sent) is counted dead; any other refused task is a mid-run refusal. Because that is a proxy, every refused task in arm C is also read by hand against the events: a mid-run refusal is confirmed to follow from the task's own fresh tool round (the prompt before it plus the round's results exceed the room), and one that turns out to be carried forward from an earlier failure is counted dead. The pass bar's part 1 is then: **zero dead tasks across t01-t05**. The first-batch arm B (1.0.3) serves as the reference: its 40 dead tasks (t01, t02 and t03 so far) and 3 mid-run refusals are counted by the same rule.
