# Deviations from PREREG.md and from the brief

Dated, in order. PREREG itself is not edited.

- 2026-10-30, before any main result: chains are 30 tasks, not 20 (brief default ~20 per session). Tasks average ~8k tokens here, so 20 tasks gave 1-2 cuts per session and no drift signal in replay. Total tasks per arm: 300 (brief: about 100).
- 2026-10-30: the ChatGPT plan cap stopped frontier calls during the pilot, so the frontier compactor and agent became a throttled secondary arm (see PREREG, Agents). The brief's single "best LLM summary" comparator is split into local (primary) and frontier.
- 2026-10-30: replay only at the 128k window (CEO), lean-cut arm C deferred (CEO).
- 2026-10-30: a first launch of chains s01 and s02 ran 4 live sessions plus 2 replay streams against mac-studio; the server answered HTTP 429 "Text request capacity is full" and Pi's default 3 retries ended some tasks within seconds. That launch was killed and its folders deleted; none of its data is used. Fix: every arm's isolated settings now retry up to 40 times with backoff, and task records carry `ended_in_error`. Concurrency is capped at about 5 streams on mac-studio (a probe showed 429s at 8).
- 2026-10-30: the next-step judge is `mac-studio/main:xhigh`, not a frontier model (PREREG already says so), to keep it off the plan cap.
- 2026-10-30, CEO steer: plan quota goes to frontier *summaries* first, in recording-name order; frontier *agent* sessions start only after every expected frontier summary exists (`harness/run_replay.py`, resource `plan-agent`). `mac-studio/main` answers the probes on all recordings, including those with frontier summaries. If the quota never recovers, claim 1 is worded against Pi's built-in compaction on `mac-studio/main`, and "at least as good as the best LLM compactors" is reported as not yet tested.
- 2026-10-30: the CTO committed no-behaviour cleanups after the pin (1576b6b, 58f5ea8, a5d708b, cea8ef4; summaries, tool text and the imported APIs unchanged per the CTO). The pin stays `d71234a`.
- 2026-10-30 19:40: chain s01 arm B died at task 8 (18:35) on a transient `docker pull` failure in the image prefetch; the harness had no retry. Its 7 finished tasks are kept outside the results (`runs/live-crashed/`), and arm B of s01 was restarted from task 1 in a fresh Pi session at 19:40, the same rule as any half-finished chain. `harness/live.py` now retries a pull up to 6 times (1-5 min waits). Chains already running keep the old code; if one dies the same way it is redone the same way.
- 2026-10-30 23:50: the mac-studio server dropped connections ("Connection error") from about 21:30 to 23:10. Every chain then running (s01 A/B, s03 A/B) had tasks that ended in a provider error or hit the 30-minute wall while the model could not answer, and s01-A died when a prompt call timed out. These four chains were set aside whole (`runs/live-crashed/outage-2026-10-30/`, not in the results) and redone from task 1 in fresh sessions. Rule applied, same for any later chain: a chain with a task that ended in a provider error is redone, since the failed task leaves error turns in the context that differ between arms. s02 (both arms) finished before the outage with no such task and stays. From this restart `harness/live.py` (a) waits for the model server to answer before it starts each task and (b) does not count time the provider spent failing requests against the 30-minute wall; the task record carries `down_seconds`. The restart also moved the pilot folders out of `runs/live` and `runs/replay` so they cannot enter a table.
- 2026-10-31 02:30: the `ended_in_error` flag also fired on tasks that hit the 30-minute wall, because our own abort ends the last assistant message with stopReason "error" ("This operation was aborted"). It means a provider failure only when the task was not aborted for wall or turns. `harness/live.py` now sets it that way and records `provider_errors`; `export_csv.py` applies the same rule to older records. A check of all events showed the redone s01 and s03 chains carry no provider error, only wall aborts, so they stay.
- 2026-10-31 (R&D finding, checked): pi-tuck's tool-loop cuts write a compaction entry to the session file but emit no `compaction_start`/`compaction_end` events, so event-based counts and latency undercount arm B (s03-B: 7 cuts in the session file, 0 events; the `cuts` field of `tasks.jsonl` has the same gap). All live cut counts and latencies now come from the session file (`analysis/sessionlog.py`): one compaction entry per cut, latency = its timestamp minus the previous entry's. For arm A this reproduces the event latency exactly (s01-A, s02-A, s03-A, all cuts). For arm B it is an upper bound on cut time (it includes anything between the last message and the cut). The `cuts` column was dropped from `live_tasks.csv`; per-cut rows are in `live_cuts.csv`. Replay cut latency (`ms` in `cuts-*.json`) is unaffected.
- 2026-10-31 (CEO steer, same finding): cuts are counted from the session files' compaction entries for both arms, and the context carried after each cut is measured from those files with Pi's own chars/4 estimate (`replay/live_after.ts` writes `cuts-after.json` per session; `analysis/sessionlog.py` reads it), the same measure replay uses for every compactor. For arm A it equals the size Pi reports for the cut, cut for cut. The claim on cut latency (PREREG Test 3a) rests on the replay measurement; live latency is reported only as a secondary upper bound (`seconds_upper_bound` in `live_cuts.csv`), since for arm B it cannot be taken from events.
- 2026-10-31 (CEO decision): a 32k live suite is added next to the main run, pre-registered in `PREREG-32K.md` before any result of it. It uses a different model (OpenRouter deepseek flash, per-token, approved by the user as the fallback; spend reported), a forced 32,768 window with reserve 8,192 for both arms (a 16,384 reserve made pi-tuck 1.0.1 refuse: "mandatory context cannot fit"; CEO approved 8,192), and pi-tuck v1.0.3 (`656f77a`) as arm B instead of the main run's 1.0.1 pin, since 1.0.1 has the small-window cut-thrash defect that 1.0.3 fixes. A third arm (1.0.1 plus the tail fix) was built and dropped on the CEO's word. Smoke runs live in `runs/smoke32*` and are not results. `harness/live.py` and `harness/run_live_all.py` gained `--suite`/`--arms`; the main run's agent dirs were checked byte-identical before and after.
